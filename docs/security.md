# Security model

- A login name resolves through the official configured Second Life name-to-agent endpoint in real mode; the immutable avatar UUID is the account key.
- Challenge responses are generic. OTPs are cryptographically random eight-digit values, expire after 10 minutes, permit five attempts, and have a PostgreSQL advisory-lock-backed 60-second resend interval. Challenge rows contain only keyed HMAC digests. Temporary outbox messages are AES-256-GCM encrypted and erased after delivery.
- Session cookies contain 256-bit random tokens; only SHA-256 hashes are stored. Cookies are HttpOnly, SameSite=Lax, and Secure must explicitly agree with `PUBLIC_SCHEME=https`.
- Browser mutation routes compare Origin with `PUBLIC_BASE_URL`. A central permission policy names each capability and is enforced again in route and service code. API denial distinguishes unauthenticated `401` from authenticated `403`; page denial redirects to the role's safe landing page.
- Administrator has every application permission and exclusively manages users/roles, terminals, and audit/security health. Manager manages inventory, rentals, reservations, and bounded rental-payment reconciliation. Agent can only search a bounded prefix for an existing Resident/Renter account, create reservations, view its own reservations, and cancel reservations it created. Renter and Resident data queries are owner-scoped; object lookups include the current user key to prevent IDOR. Resident cannot initiate checkout.
- Role changes are serialized, prevent demoting the last active Administrator, are audited, and transactionally revoke the target user's sessions. New verified users default to Resident; legitimate reservation/lease assignment promotes Resident to Renter without automatic downgrade.
- Destructive management actions require a bounded reason and write it into the same transaction's audit record, including role changes, reservation cancellation, rental termination, listing unpublish, and terminal rotate/revoke/rebind.
- CSP, frame denial, MIME-sniff protection, referrer policy, and restrictive permissions policy are set at the edge. Protected data is `no-store`.
- Real adapters refuse startup without SL and Stripe credentials. The checked-in Compose stack is development simulation; production refuses simulation unless an operator explicitly overrides the guard. Simulation OTPs are available only through direct database operator tooling, never HTTP.
- Stripe uses the exact raw body for signature verification, durably records every relevant event and processing state, binds session/reference/invoice, checks snapshotted amount and currency under row lock, and never activates a lease from the success page. Late charges are recorded for reconciliation and transactionally enqueue a durable provider action; the bounded payment worker retries the same Stripe idempotency key until an authoritative terminal result is stored.
- Every terminal has a distinct secret encrypted at rest with AES-256-GCM. Requests bind exact body hash, timestamp, nonce, event ID, object UUID, owner UUID, and shard. LSL and the server use Base64 HMAC-SHA256 with constant-time comparison; timestamps allow ±5 minutes, and nonces/event IDs are persisted.
- OTP creation and verification use atomic PostgreSQL fixed-window counters for canonical account names and client IPs. `X-Forwarded-For` is accepted only when `TRUST_PROXY=true`.

ADMINISTRATOR terminal APIs provision, bind, list, revoke, rebind, and rotate credentials. Plaintext is returned once; only AES-GCM ciphertext is stored. Rotate web secrets by invalidating outstanding challenges/sessions. Production secrets belong in an orchestrator secret store, never Compose or images.
